# App profile

Extends the SDD contract ([`sdd_contract.md`](sdd_contract.md), templates in [`sdd_templates.md`](sdd_templates.md)) from one task to a whole application. It adds the documents, gates, and checks that exist once per app; every task opened under it is an ordinary task of the contract and lists `app` in `status.md` → `profiles`. Where this file and the contract differ, the contract wins.

## Terms

- **App**: the whole product the human asked for. One per `{root}`.
- **App kind** — recorded in `app.md` and `app_status.md`:
  - `presentation`: interactive HTML that tells a story or shows information. No stored user data, no sign-in, no backend.
  - `prototype`: clickable screens that look like the app and show its flows with invented data. No real logic, no real data, no backend.
- **Fidelity** — recorded in `app.md` and `app_status.md` for a `presentation` and a `prototype`; `n/a` for the other kinds:
  - `high` (the default): an offline, responsive, animated React app on invented JSON data, packaged as one HTML file, as [`packaged_web_app.md`](packaged_web_app.md) says. A `prototype` keeps the person's changes in the browser; a `presentation` keeps them only while it is open.
  - `standard` (only when the human asks for a quick sketch): a `prototype` is one `feature-preview-kit` preview per feature, with no app code; a `presentation` is static HTML without a UI framework.
  - `poc`: working code that proves one or two risky ideas end to end. Not for real users' data.
  - `mvp`: the first version real users can use. Every journey in `app.md` works end to end.
- **Backlog item**: one row of `backlog.md`. It becomes exactly one task.
- **Backend**: a server-side component of the app — an API the client calls.
- **Operation**: as the contract's **Approvals** defines it.
- **IDs** added by this profile, under the contract's ID rules: `J` user journey, `N` app-level requirement, `SC` success criterion, `BL` backlog item, `RK` risk, `OP` operation, `GAP` gap.
- **`status.md` key** added by this profile: `backlog_item`.

## Layout additions

```
{bundle}/
  project/
    app.md                 # what the app is and why (A1)
    app_status.md          # app-level phase state, approval mode, approvals, handoff note
    design_system/         # the base (feature-preview-kit, Phase A) (A2)
    backlog.md             # the only backlog (A4)
    backlog_tracker.md     # generated by scripts/backlog.js — never edited
    backlog.html           # generated by scripts/backlog.js — never edited
    risks.md               # risk register (A5)
    operations.md          # every operation asked, with its decision
    handover.md            # project handover (A6)
    evidence/              # app-level videos and scan reports (handover)
  features/{feature}/
    preview/               # feature preview (feature-preview-kit, Phase B)
    tasks/{task_id}/
      evidence/            # videos, screenshots, traces, scan reports of the task
```

- Concept documents and their `type`: `app.md` — `App Intent`; `app_status.md` — `App Status`; `backlog.md` — `Backlog`; `backlog_tracker.md` — `Backlog Tracker`; `risks.md` — `Risk Register`; `operations.md` — `Operations Log`; `handover.md` — `Project Handover`.
- All are listed under `# Project` in the bundle `index.md`, as are `* [Backlog board](project/backlog.html) - Clickable view of the backlog and its progress.` and `* [Design system](project/design_system/config.json) - {base name and version; locked | neutral kit}`.
- `design_system/` and `preview/` are written only through the `feature-preview-kit` skill, run with `--root {root}`.
- **`evidence/`** holds media and raw reports only; every result of record is a row in `validation.md`. Evidence shows seeded test data only — never a real person's data or a secret. Whether `evidence/` is committed is asked with G0; the default is to add `{bundle}/**/evidence/` to the repository's ignore file, and a `Run log` note then says `local only`.

## App phases and gates

`app_status.md` frontmatter is the single record of app-level phase state; its `Approvals` table is the single record of app-level gate decisions.

| Step | Field and states | Gate | Approves |
|---|---|---|---|
| 1 | `phase_app_intent: pending → in_review → approved` | **A1** (asked with G0) | `app.md`: app kind, platforms, journeys, requirements, success criteria, out of scope; the approval mode and the task track |
| 2 | `phase_design_system: pending → in_review → approved` | **A2** | the locked base and its style guide |
| 3 | `phase_architecture: pending → in_review → approved` | **A3** | `architecture.md`, the stack decisions, the conformance rules, whether there is a backend |
| 4 | `phase_backlog: pending → in_review → approved` | **A4** | `backlog.md`: items, order, priorities |
| 5 | `phase_risks: pending → in_review → approved` | **A5** | `risks.md`: every risk's response, and the backlog items they add |
| 6 | `phase_tasks: pending → in_progress → done` (`blocked` while a blocker needs the human) | each task's G1–G4 | per the contract |
| 7 | `phase_handover: pending → in_progress → in_review → accepted` | **A6** (asked with the handover task's G4) | the finished app, `handover.md`, its gaps and open risks |

- Any phase may be `reverted` (SKILL.md → *App-level revert*). No phase is skipped: the rigor table decides how much each step holds for an app kind.
- `next: Intent | Design system | Architecture | Backlog | Risks | Build | Handover | done` always names the step to resume.
- The contract's gates keep their meaning. A1–A6 are never reordered; A1 is asked with G0, A5 may be asked with A4 for a `presentation` or `prototype`, A6 is asked with the handover task's G4; no other batching.

## Approval modes

The mode is the human's standing instruction about reviews. It is asked in the opening message of a new app (SKILL.md → *Opening message*), as question 1, one line per option, in these words or shorter ones, `auto-technical` first and marked recommended — most people who vibe-code an app want to decide what it does and how it looks, not review technical documents:

- `auto-technical` (recommended) — "Ask me about what the app does, how it looks, what is in scope, and the final result; decide the technical steps yourself, including accepting each finished piece."
- `auto-all` — "Don't stop for reviews; decide everything yourself, including accepting each finished piece and the final result. I'll look at the end."
- `review` — "Show me each step and wait for my OK."

Record it as `approval_mode` in `app_status.md` and as an `Approvals` row with gate `MODE`, quoting the human's words. Until the human chooses, `approval_mode` is `not-chosen`: every gate waits for the human, as in `review`, and no `MODE` row is written — silence or a missing answer is never auto-approve. The human may change the mode at any time by saying so; add a new `MODE` row. This record is the project document the contract's **Scope of auto-approve** requires, so the mode carries across tasks and sessions.

**Later sessions**: the opening message of a session that resumes the app shows the workflow and the recorded mode. While the mode is `review` or `not-chosen`, it offers the auto modes again and waits for the answer; in an auto mode it names the mode, says how to change it, and the work continues. A role started with a brief (code reviewer, QA tester) never asks.

| Gate | `review` (and `not-chosen`) | `auto-technical` | `auto-all` |
|---|---|---|---|
| G0 + A1 app intent | human | human | auto |
| A2 design system | human | human | auto |
| A3 architecture and stack | human | auto | auto |
| A4 backlog | human | human | auto |
| A5 risks | human | auto | auto |
| task G1, G2, G3, G4 | human | auto | auto |
| A6 handover | human | human | auto |
| `OP` operations | human | human | human |

- `auto` = the contract's auto-approve: decision `auto-approved` by the agent actor, notes quoting the `MODE` row, each choice the human would have made listed under `Assumptions`. Every document is still written in full, and every check below still has to pass.
- In `auto-technical` and `auto-all`, plan no `manual` validation case: each state the human would have checked is an automated `e2e` case with recorded evidence. This is what lets G4 be auto-approved under the contract.
- In `auto-all` the interview still runs one round; an unanswered question is `defaulted` and logged.
- The human is always invited to try a finished task and the finished app; in an auto mode the work does not wait for it.

## Operations

Operations are approved separately from every gate, in every mode.

| Category | Examples |
|---|---|
| `setup` | installing a runtime, a package manager, a container runtime, a test browser, a simulator, the scanner; pulling a container image; creating an account, a project, a key, or a database on a service |
| `update` | upgrading or removing system software or a global tool; changing a system or service setting |
| `delete` | deleting files or data the task did not create; dropping or resetting a database that holds anything but seeded test data |
| `publish` | pushing to a remote, opening a pull request, releasing a package or a build, sharing a link or a file outside the workspace |
| `deploy` | releasing the app or a part of it to any hosted environment; running a migration against a hosted database |

- Installing, inside the workspace, the dependencies an approved plan lists is not an operation. Starting and stopping the app's own local containers from approved images is not an operation.
- **Request**: before each operation, ask the human in plain words: the exact action (the command or the click), its target, why it is needed, what it costs if anything, and how to undo it. Several actions may be asked in one message; each is one row, and the approval covers exactly the listed actions. An approved action may be repeated unchanged; a changed command or target is a new operation.
- **Record**: one row per action in `project/operations.md`, added as `pending` before asking, with the decision, the actor, the time, and the human's words set once.
- **Never done by the agent**, whatever the approval: typing a password, key, token, or payment detail anywhere — ask the human to do it and continue when they say it is done. Record only the *name* of a secret, never its value.
- A `publish` or `deploy` request lists every `high` risk that is not `closed` and every open gap.
- A declined or unanswered operation is not performed. If the work cannot continue without it: a blocker in the task, a risk row, and the turn ends.

## App kinds and rigor

Derive the app kind from the request and confirm it at A1. When in doubt between two, propose the smaller one and say what the larger would add.

| | `presentation` and `prototype`, `fidelity: high` | `presentation`, `fidelity: standard` | `prototype`, `fidelity: standard` | `poc` | `mvp` |
|---|---|---|---|---|---|
| Deliverable | one packaged HTML file that opens offline without a server ([`packaged_web_app.md`](packaged_web_app.md)) | static HTML that opens without a server | one clickable preview per feature | a working app of narrow scope | a working app covering every journey |
| A1, A2, A4, A6 | required | required | required | required | required |
| A3 architecture | required — client only, with the packaged-app rules `W1`–`W10` | required — client only | one decision: "the previews are the deliverable"; no stack | required | required |
| A5 risks | required; may be asked with A4 | required; may be asked with A4 | required; may be asked with A4 | required | required |
| Backend | never | never | never | only when the stack guide's *Is a backend needed?* says so | same |
| Foundation item first | yes | yes | no | yes | yes |
| Automated tests | `unit` for view models, the data service, strings, and seed; an `e2e` case per journey against the packaged file, offline | an `e2e` browser case per journey | an automated walk of every preview path | `unit`, `integration`, and `e2e` | same |
| Independent code review | no | no | no | yes | yes |
| Independent QA run | optional — asked at A3, default no | optional — asked at A3, default no | optional — asked at A3, default no | asked at A3, default yes | asked at A3, default yes |
| Dependency audit | yes | when it has dependencies | no | yes | yes |
| Security scan | no | no | no | when the app has a backend | when the app has a backend |
| Logging baseline | client rules | client rules | no | all rules | all rules |
| Security baseline | client rules | client rules | no | all rules | all rules |
| Video evidence | when the runner can record | when the runner can record | when the runner can record | when the runner can record | when the runner can record |

- **Independent QA run** is decided once, at A3, for the whole app — every task and the handover — and recorded as `qa_run` in `app_status.md` with a `project/decisions.md` row (source `A3`) quoting the human's words or naming the default. The default is `no` for a `presentation` or `prototype` (their automated `e2e` cases still run on every task) and `yes` for a `poc` or `mvp`. In a mode that auto-approves A3, the default applies, is logged under `Assumptions`, and the A3 report names it. The human may change it at any time: a new decision row; it applies to tasks not yet validated.
- A `prototype` task with `fidelity: standard` writes `ux_design.md` in its Design phase and builds the feature's preview in its Build phase: the preview's source files are its `Module map`, and the kit's own checks are its validation cases.
- A task of an app with `fidelity: high` writes `ux_design.md` in its Design phase (no kit preview unless the human asks) and builds product code in its Build phase, under [`packaged_web_app.md`](packaged_web_app.md).
- When the security scan is required but the scanner cannot be run — its setup operation is declined, or the machine cannot run it — add a `high` risk row `security scan not run` with response `defer` and the trigger `before any publish or deploy`, mark the scan command `unavailable` in `architecture.md` → `Commands`, and plan no scan case. It is then a gap in the handover.

## Additions to task documents

Each block is added after the core sections of the named template — and after any section another profile adds — keeping the core sections unchanged.

### `status.md` frontmatter

```yaml
profiles: [app]            # plus any other profile the task uses
backlog_item: BL{n}
```

### `intent.md`

```markdown
## App context (required)
- **Backlog item**: [BL{n}]({relative path to backlog.md}) — {item}
- **Covers**: {J, N, and SC IDs of app.md}
- **Mitigates**: {RK IDs | none}
- **App kind**: {app kind} — the rigor that applies is in the plan's `Stop criteria`
```

### `plan.md`

```markdown
## Stop criteria (required)
**Done when** — every line names the validation case or checklist item that proves it:
- every acceptance criterion passes ({V IDs})
- {each check the rigor table requires for this app kind: independent review, independent QA run (when `qa_run: yes`), dependency audit, security scan — with its V ID, or `n/a: {reason}`}
- every `Conformance checklist` item passes with evidence

**Stop and ask when** — the agent ends the turn and records a blocker; it never works around one:
- the same failure has been tried three times
- an operation is needed: {each operation this task needs, with its `OP` ID | none}
- a secret, an account, or a payment is needed
- the work needs a file, a dependency, or a behaviour the plan does not list
- {task-specific condition | none}
```

### `validation.md`

No added sections. The `Validation plan` holds, besides the cases for the acceptance criteria, one case for each check the rigor table requires:

| Check | Level | Expected result |
|---|---|---|
| Independent code review | `static` | no open `blocker` or `major` finding |
| Independent QA run (when `qa_run: yes`) | `e2e` | every `e2e` case passes when run by the QA role; no acceptance criterion is without a case |
| Dependency audit | `static` | no known vulnerability rated high or critical |
| Security scan (a task that adds or changes an HTTP route, or a page served to a browser) | `e2e` | zero High and zero Medium alerts |
| Traceability (a task that adds a request path) | `integration` | one correlation ID is found in the log lines of every layer the request crosses |

Each run is a `Run log` row whose `By` is the actor that ran it and whose notes give the independence level (`sub-agent`, `fresh session`, or `same agent`) and the evidence path. Each finding is a `Defects` row.

## Checks

**App intent validation** (before A1):
1. Frontmatter is valid; `app_kind`, `platforms`, `delivery_target`, and `fidelity` (`high` or `standard` for a `presentation` or `prototype`, `n/a` otherwise) are set; every required section is filled or `n/a`.
2. Every journey names its user, its steps, and its outcome; every journey has at least one success criterion; every success criterion states a result a person can see. For a `prototype` with `fidelity: high`, `Showcase` lists at least one feature, each naming a journey that exists.
3. Every statement names its source (`user`, `repo:<path>`, `file:<name>`, or `derived`).
4. A technology is named only as a constraint with its source.
5. No `Open questions` row is `open`; in an auto mode an unanswered one is `defaulted`, with its default under `Assumptions`.
6. No secret, personal data, or invented external reference.

**Architecture completeness** (before A3):
1. Every platform in `app.md` has a client stack; `has_backend` is `true` or `false`, with the reason as a decision row; `qa_run` is `yes` or `no`, with its decision row.
2. Every stack choice has a `project/decisions.md` row with a reason and a rejected alternative; no version number was written from memory.
3. `architecture.md` has every template section; `Structure` gives each layer's allowed and forbidden dependencies; `Commands` lists set-up, run, build, lint, test, `e2e`, and — where the rigor table requires them — audit and scan.
4. `Conformance rules` holds every engineering-baseline rule that applies to the app kind, each with its own `C` ID; with `fidelity: high`, also the packaged-app rules `W1`–`W10`.
5. Every operation the build needs is a row of `operations.md`.
6. For a stack the human gave: every review finding is a risk row or an answered question.

**Backlog completeness** (before A4):
1. Every `J`, `N`, and `SC` of `app.md` is in the `Covers` cell of at least one item; every item covers something or is of kind `enabling`.
2. Every item is one feature or one technical outcome, has an outcome sentence in plain language, a kind, a task type, and a priority.
3. Dependencies name existing items and form no cycle; the order respects them.
4. Where the rigor table requires a foundation item, it is first; the handover item is last.
5. `backlog check` passes: the tracker and the board are current.

**Risk completeness** (before A5):
1. Every risk has a category, a likelihood, an impact, the level the template's table yields, a response, an action, an owner, and a status.
2. Every `avoid` and `mitigate` risk links to a backlog item or a conformance rule that exists; every `transfer` names who takes it; every `defer` names its trigger; every `accept` gives its reason.
3. Every finding of a stack review, every data class `personal` or `secret` in `app.md`, and every external service has at least one risk row.

**App hard gate** (before opening any task): `phase_app_intent`, `phase_design_system`, `phase_architecture`, `phase_backlog`, and `phase_risks` are each `approved` for the documents' latest revisions (`app_revision`, `backlog_revision`, and `risks_revision` equal them).

**Plan completeness** — additions: `backlog_item` is set; `App context` and `Stop criteria` are filled; the validation plan has every case the rigor table requires for the app kind; the `Conformance checklist` lists every applicable baseline rule; in an auto mode no case is `manual`.

**Validation completeness** — additions: each required check has a run made after the last code change; no `blocker` or `major` review finding is open; the security scan, where planned, reports zero High and zero Medium alerts; a run made by the same agent is named as such in the `Run log`.

**Handover completeness** (before A6):
1. Every backlog item is closed or `removed`, or is listed in `handover.md` → `Not delivered`.
2. Every success criterion of `app.md` has a result from a run against the finished app.
3. `Gaps` lists every item not delivered, every check not run or run by the same agent, every `manual` case without a result, and every `Known limitations` entry of the feature specs. Exception: with `qa_run: no` on a `presentation` or `prototype`, the QA run is not a gap — `Quality evidence` says `not run — optional, skipped by choice`. On a `poc` or `mvp`, `qa_run: no` is a gap.
4. `Open risks` lists every risk that is not `closed`; `How to run` uses only commands recorded as run in `architecture.md`.
5. No secret value appears in `handover.md`, the `README`, or the evidence.
